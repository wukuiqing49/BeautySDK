# 当前SDK性能评估（2026-10-30）

结论：架构已有实时处理所需的异步、有界与纹理合成基础，基础美颜/调色可以作为限定范围试用；尚没有证据证明最新版本在有效人脸、复杂效果叠加及热稳态下稳定达到30/60FPS。主要已测压力在模型分析的新鲜度；GPU多通道渲染、整体内存与长期温升仍缺完整测量。本轮为源码与历史证据审阅，没有启动新一轮相机/模型性能测试，没有改变功能或推进性能基线。

## 当前实现的有利点

- 相机/引擎回调提交分析副本，模型在独立worker创建/使用/关闭；忙时丢弃或覆盖最新待处理帧，不保留无限视频队列。DirectByteBuffer复用，模型输入转换和蒙版后处理走现有C++路径，无逐帧Bitmap主线。
- 高清纹理用于GL美颜与合成，分析使用小图。只有纹理输入的宿主可选双PBO/fence桥接，Demo用独立RGBA支路；不能将此描述为模型零拷贝。
- 公共SDK根据效果需求启停人脸/手势/背景。手势默认关闭、单在途，默认100ms采样间隔，理论最多约10次分析/秒，实际受推理耗时限制。模型文件放在包内本身不等于持续运行。
- 3D姿态缓存复用同一次真实观测，只在变化时更新相应遮挡顶点；资源加载离开渲染帧路径，最近增加缩略图与组合像素预算。没有测量缓存改动带来的具体FPS收益，不给出提升百分比。

## 当前瓶颈与限制

### 1. 模型结果更新与画面渲染不同步

视频可以继续渲染，同时使用最近有效的分析结果，因此49ms分析不等于预览帧率被限制为20FPS。但一次49ms的同步分析说明此夹具的模型更新速度约处于20次/秒量级；还要考虑复制、排队及发布。CPU127ms对应更慢的更新，动态跟随容易落后。

3D只接受真实且150ms内的姿态。此前OPPO复现窗口记录过160.54ms采样年龄并触发STALE隐藏，属于已经观察到的性能影响；之后GPU优先候选仍被用户报告闪烁，不能把旧过期数据当成新闪烁的全部根因。无脸、错误、排队与渲染仍须同步排查，不能靠延长有效期掩盖。

### 2. 高清GPU带宽与纹理内存

`core/lib_beauty_gpupixel/src/main/cpp/beauty_bridge.cpp`声明五个Target，Allocate对全部Target按输出尺寸分配RGBA纹理；磨皮使用归一化、双向模糊、差分、合成等绘制阶段，其他调整继续增加绘制。1080p时仅这五份RGBA颜色存储的理论像素量约39.55MiB，720p约17.58MiB；不是实际驱动分配实测，尚未包含LUT、相机、场景/3D纹理及深度缓冲。

当前没有GPU定时查询数据证明1080p或多效果叠加的实际GPU耗时。优先评估按需分配中间Target、模糊降采样及复用通道；变更必须与清晰度/肤质对照，不能直接降低画质当优化完成。

### 3. 默认观察与可选多模型负载

Demo按用户要求默认允许观察人脸/手势，可能在未启用视觉效果时仍运行分析。`PreviewRequest`与公共SDK按需开关应分别解释，不能把Demo默认负载等同于SDK不可关闭的固定开销。人脸、手势和背景同时开启会竞争CPU/GPU/内存带宽，当前缺有效人脸/手势覆盖的联合长测。

禁用实际运行的手势支路可能减少计算和模型工作集；仅从包内删除一个已经停用的模型主要减少APK体积，不保证其他效果FPS提升。

### 4. 指标覆盖不足

`BeautyPerformanceMeter`只计新采样处理的CPU提交耗时和本地process频率，gpuExecutionNs仍为null。没有测得GPU执行、相机曝光至显示、编码/网络/远端时延。不能用提交P95 3.69ms推导完整流程能稳定达到约270FPS，也不能将Demo约400MiB PSS全部归因于SDK。

## 优化与验收顺序

1. 固定设备、输出分辨率、前后摄、delegate与效果，先补GPU耗时和处理/显示/分析三个频率的区分；同时记录结果年龄P50/P95、过期/无脸/错误占比。
2. 以有效人脸覆盖率为前置门槛，依次测原图、纯基础美颜、人脸＋美型/贴纸、背景、3D，再测与手势叠加。先720p再1080p，不把分析320小图结果写成1080p性能。
3. GPU每帧预算以30FPS的33.3ms、60FPS的16.7ms作为全链路目标参考；还要给相机和显示等步骤留空间，检测分支独立评价更新率和年龄，不要求每个模型跟视频同频。
4. 每组预热后延长至热稳态，至少30分钟记录CPU、PSS/原生/GPU内存、GC、掉帧、温度/热状态及耗时趋势。当前短样本未完成这一项，也没有实际直播引擎的远端验收。
5. 先消除主要配置下的3D闪烁与分割尾部延迟，再按实测热点推进中间纹理/分析节流优化。商用品质、稳定30/60FPS、低端机支持不作为当前已验证结论。
